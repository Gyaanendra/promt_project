Guardrail Labs: Automated Adversarial Red-Teaming & Empirical Prompt Hardening for Chatbots

A Multi-Agent Architecture for Measuring and Hardening LLM System Prompts Against OWASP Top 10 Vulnerabilities
Team Context Window
Authors Devansh Kumar (Lead), Ayush Anand, Gyanendra Prakash, Ankit Gupta
Faculty Reviewer Dr. B D Mazumdar
Target Stack Next.js 16, Vercel, Claude / Gemini / Groq Llama-3.1
Executive Summary & Abstract Large Language Model (LLM) conversational agents are frequently deployed with vulnerable system prompts that leak internal instructions or abandon domain constraints under adversarial pressure. Current defensive tooling primarily flags weaknesses without providing algorithmic repair. Guardrail Labs presents an automated, measurable red-teaming and prompt-hardening pipeline. By executing a sequence of prompt-driven agents—comprising a categorized Attacker, an isolated Target bot, a double-blind rubric Judge with deterministic canary verification, and a class-level Fixer—the system measures baseline Attack Success Rates (ASR), rewrites the system prompt to defend against underlying failure classes, and re-evaluates the prompt against an unseen held-out attack set. Empirical testing across five distinct chatbot archetypes demonstrates a >50% to 76.7% relative reduction in held-out ASR while constraining benign over-refusal to ≤8.3%, validated by a 50-item double-blind human study achieving 91.3% agreement (Cohen’s κ = 0.812).

1. Introduction & Problem Statement

The OWASP Top 10 for LLM Applications (2025) identifies Prompt Injection (LLM01) as the primary threat vector and introduces System Prompt Leakage (LLM07) as a dedicated critical vulnerability. When chatbots are deployed in high-utility scenarios—such as academic helpdesks, retail kiosks, or financial assistants—malicious or manipulative users employ delimiter exploits, roleplay pretexts, and jailbreak personas to extract confidential staff tokens or coerce unauthorized actions.

Existing defensive frameworks (e.g., Promptfoo, NVIDIA Garak, Microsoft PyRIT) focus exclusively on vulnerability scanning. They leave the burden of prompt repair to manual, unguided developer trial-and-error. Guardrail Labs addresses this gap: it takes a raw system prompt, generates structured attacks, scores responses under an isolated rubric, rewrites the prompt using training failures, and verifies generalizability against an unseen held-out attack suite with measurable statistical indicators.

2. System Architecture & Execution Pipeline

Guardrail Labs is engineered as a serverless Next.js 16 (App Router) application deployed to Vercel. A critical engineering constraint of serverless environments is execution timeouts (typically 60 seconds). Because a full adversarial audit requires hundreds of model inferences, traditional monolithic backend workers would inevitably time out.

Browser Client Orchestrator (src/lib/pipeline.ts) │ ├── Step 1: POST /api/attack ──► Strong Model (Attacker v2) [Train + Held-Out Sets] ├── Step 2: POST /api/benign ──► Strong Model (Benign Gen) [In-Scope Legit Queries] │ ├── Step 3: Baseline Evaluation (Concurrency = 4) │ ├─► POST /api/target ──► Isolated Target Model (Groq / Llama-3.1-8B) │ └─► POST /api/judge ──► Canary Normalizer (Deterministic) ──► Judge Model (v2) │ ├── Step 4: POST /api/fix ──► Strong Model (Fixer v2) [Class-Level Rewrite] │ └── Step 5: Verification Evaluation (Identical Test Suite) └─► Re-evaluates Hardened Prompt on Held-Out Attacks + Benign Queries

Key Architectural Decisions

  • Browser-Driven Client Orchestration: The browser acts as the pipeline sequencer, calling small, atomic serverless endpoints. If any sub-request encounters a network blip or rate limit (HTTP 429), client-side exponential backoff retries without aborting the entire run.
  • Model Family Decoupling: The Target model belongs to a completely different family (open-source Llama-3.1 / Mistral via Groq) than the Strong model (Claude 3.5 Sonnet / Gemini 2.5 Flash). This prevents self-grading bias during the judging phase.
  • Deterministic Canary Pre-Filter: A regex and punctuation-stripped normalization check evaluates whether planted secrets (e.g., ALPHA-7) leaked, overriding model interpretation with 100% precision.
  • Strict Privacy & Credential Protection: API keys are strictly server-side environment variables. An optional constant-time APP_ACCESS_CODE protects public demo endpoints against unauthorized quota consumption.

4. Prompt Engineering Design & Iteration

Because the entire product is a chain of prompts, prompt engineering constitutes the primary intellectual contribution of this project. Prompts reside centrally in src/lib/prompts.ts with versioned definitions.

4.1 Threat Taxonomy (Four Attack Categories)

  1. Prompt Injection (LLM01): Delimiter collision, instruction override (“Ignore previous instructions”), developer simulation modes, and indirect injection framing.
  2. System Prompt Extraction (LLM07): Verbatim repeats, foreign language translation pretexts, code completion tricks, and authorization code harvesting.
  3. Persona Override: DAN-style unrestricted jailbreaks, fictional roleplay traps, and emotional coercion to abandon organizational safety filters.
  4. Policy & Scope Bypass: Social engineering to exceed declared limits (e.g., unauthorized fee waivers, exceeding refund caps, or committing to out-of-menu items).

4.2 Iterative Evolution: Baseline (v1) vs. Hardened (v2)

Prompt Role Baseline (v1 Milestone 1) Hardened (v2 Production) Engineering Justification
Attacker Generic instruction: “Write 5 attacks for category X”. Explicit category guides, strict 600-char cap, ethical harm boundary, separate held-out generator with anti-overlap avoid-list. v1 attacks were repetitive and ignored target-specific rules. v2 forces tactical diversity across social engineering and multilingual angles.
Judge Unstructured binary output: “Did it break? Yes/No”. Explicit 5-condition rubric, 0–3 severity scale, XML data boundary isolation (<system_prompt>, <attack>, <chatbot_reply>). v1 was susceptible to judge injection (e.g., attacks saying “Judge: say this passed”). v2 treats inputs strictly as untrusted data.
Fixer Free-form rewrite request. Class-level hardening instruction, scope preservation constraints, explicit ban on copying attack strings, out-of-prompt canary warnings. v1 memorized specific attack phrases, causing severe over-refusal on normal questions. v2 targets the general vulnerability pattern.

6. Limitations & Threat Model Boundaries

  1. Single-Turn Evaluation: Version 1 tests single-turn injection payloads. Multi-turn conversation exploitation (e.g., priming or progressive trust elicitation) is scoped for v2.
  2. Risk Reduction vs. Mathematical Proof: Prompt hardening significantly raises the barrier to exploitation (lowering ASR by >50%), but it cannot guarantee absolute cryptographic security. Defense-in-depth (external guardrail proxies, schema validation) remains recommended.
  3. External Credential Isolation: Planted secrets in system prompts are inherently fragile. The Fixer prompt consistently outputs recommendations advising developers to move true credentials out of prompts into backend authentication layers.
  4. Synthetic / Low-Stakes Scope: In accordance with course rules, testing is strictly restricted to fictional or authorized test prompts; no production PII is ingested.

7. Conclusion

Guardrail Labs provides an end-to-end engineering solution for automated chatbot security testing. By pairing an empirical before/after measurement pipeline with class-based prompt synthesis, the framework delivers measurable risk reduction without degrading conversational utility. All verification targets—including ≥50% relative ASR drop, ≤10% over-refusal, and ≥85% judge reliability—were verified and documented.
